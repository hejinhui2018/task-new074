# StateVault · 本地状态迁移验收台

模拟一个复杂工作台把状态保存在浏览器里、老用户跨多个版本直接回来的场景，用来验收**本地状态迁移**的安全性。
React + TypeScript + Vite，零运行时依赖（除 React 外）。

## 启动

```bash
npm install
npm run dev      # 交互验收台  http://localhost:5173
npm test         # 程序化断言：12 组场景 / 97 个断言（Node 内存存储）
npm run build    # 类型检查 + 生产构建
```

## 这个验收台在验证什么

老做法：迁移直接在主快照上原地改，中途失败会留下「半新半旧」的数据，下次打开继续报错。

StateVault 的每一步迁移都走原子提交协议：

1. **预写暂存日志（WAL）**先落盘：记录 `from/to/phase/runNonce`；
2. **纯内存转换**——转换函数抛异常时主快照一个字节都不动；
3. **提交前校验产物**（每版一组 `outputChecks`），不合格的半成品进**隔离区**而不是覆盖主快照；
4. **回滚快照先行落盘**（上一个已验证完好版本），再整体替换主快照；
5. 暂存标记 `committed` 后清除。

刷新恢复依据 WAL 判定：

- 日志停在 `staged`、主快照仍是旧版 → 提交从未发生，丢弃半成品、旧快照完好；
- 主快照已是 `to`（无论日志有没有来得及标 committed）→ 只清日志，**迁移绝不重跑**（版本号 + WAL 双重幂等）；
- 主快照 JSON 损坏 → 坏字节进隔离区，可用回滚快照恢复，隔离区里的坏数据原样保留。

## 数据结构（v1 → v5）

| 版本 | 关键形态 |
| --- | --- |
| v1 | `user`、`panels: string[]`、`tasks: 数组`，theme 不约束（出厂数据含脏值 `'blue'`） |
| v2 | user 补 email、panels 变对象数组、tasks 补 order、theme 归一化 |
| v3 | `profile/layout` 重组、tasks 改 **id 索引**、补 createdAt |
| v4 | 任务 priority、profile.emailVerified、layout.density、filters |
| v5 | 任务 tags、locale、theme 放开 `system`、updatedAt |

另有模拟的 **v7 未来数据**：当前客户端不认识，只降级只读、不迁移、不回写。

## 操作能力

- **单步 / 自动运行 / 暂停**（节奏可调，0.3–3 秒/步）
- **故障注入**（可提前挂到任意后续步骤，触发一次）：
  - 迁移函数抛异常
  - 产物校验失败（故意删字段）
  - 转换前断电、提交后断电（进程锁定，必须「刷新恢复」）
  - 主快照半截写入
- **撤销 / 重做**（会话级检查点）、**刷新恢复**（重建引擎，从 localStorage 重读）、**重置**
- **场景装载**：v1 跨 4 版老用户 / v3 跨 2 版 / 未来 v7 只读 / 损坏快照
- 检查器四个页签：当前状态、暂存与回滚快照、隔离区（含坏数据原文与校验问题）、运行日志

localStorage 键位：`statevault:doc`（主快照信封）、`:staging`（WAL）、`:rollback`（回滚快照）、`:meta`（隔离区 + 日志）。

## 程序化验收（`npm test`）

1. 跨多版 v1→v5，脏 theme 归一化、字段逐级保留
2. 幂等：重跑不重复应用；撤销后重跑结果一致
3. 中途校验失败：半成品隔离、主快照停留旧版、排除故障后续跑
4. 迁移函数异常：主快照与磁盘保持干净
5. 转换前断电 → 刷新丢弃半成品，可继续
6. 提交后断电 → 刷新识别已提交，迁移不重放
7. 主快照写坏 → 刷新隔离、回滚恢复且不覆盖坏数据
8. 未来 v7 → 降级只读，磁盘一字节不改
9. 启动即损坏、无回滚快照 → 安全失败
10. 撤销 / 重做
11. v3 老用户跨 2 版 + 重置
12. 相同坏产物指纹去重，隔离区不产生重复档案
